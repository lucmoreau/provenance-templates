A provenance template is a PROV document [[PROV-DM]] in which some identifiers, attributes and values are variables. A set of bindings associates values with the variables, and instantiation replaces the variables by their values to produce an ordinary PROV document. This document specifies the artefacts of the provenance template approach: templates, their variables and the tmpl: vocabulary; the JSON representation of bindings; bindings schemas, which describe the variables of a template; template indexes; and template transformation files, which automate the instantiation and merge of templates. It also describes, non-normatively, the command-line tools, the executables, the Maven plugin and the template compiler of ProvToolbox [[PROVTOOLBOX]] that process them. The algorithms are specified in [[PROV-TEMPLATE-ALGORITHMS]].

This is an unofficial draft, part of the PROV-TEMPLATE family of documents [[PROV-TEMPLATE-OVERVIEW]]. It has no official standing of any kind and does not represent the consensus of any standards organisation.

This document revises and extends PROV-TEMPLATE: A Template System for PROV Documents [[PROV-TEMPLATE-2014]], edited in 2014 by Danius Michaelides, Trung Dong Huynh and Luc Moreau. The definitions of templates and of the representation of bindings as PROV documents come from that draft; its algorithm is replaced by that of [[PTM-BOOK]], specified in [[PROV-TEMPLATE-ALGORITHMS]]. lists the changes.

The JSON Schemas included in this document are copies of those distributed with ProvToolbox (branch development2_0, commit 95386ae29, 2026-10-16) and with the template library. Editor's notes mark where this document, the schemas and ProvToolbox currently disagree.

A template processor is software that instantiates templates with bindings, or merges templates or documents, according to this specification and [[PROV-TEMPLATE-ALGORITHMS]]. A template processor conforms to this specification if it accepts every conforming template, set of bindings and template transformation file, and processes them as specified.

Introduction

Provenance often follows patterns that repeat during the lifetime of an application. Provenance templates declare such patterns once, in PROV itself, with variables acting as placeholders for values; the pattern is instantiated many times, each time with a new set of bindings for the variables. The code that instruments the application only collects values, and the generation of provenance is left to instantiation [[PROV-TEMPLATE-TSE]]. [[PROV-TEMPLATE-OVERVIEW]] presents the approach and [[PROV-TEMPLATE-PRIMER]] introduces it through an example.

This document is organised as follows.

  • defines templates, their variables and the reserved tmpl: attributes.
  • defines bindings and their JSON representation.
  • defines bindings schemas.
  • defines template indexes, by which templates are found by identifier.
  • defines template transformation files.
  • , non-normative, describes the ProvToolbox tools that process these artefacts.

Conventions

Unless otherwise stated, examples use the PROV-N notation [[PROV-N]]. The term qualified name is used as in [[PROV-DM]], with the syntax of the production QUALIFIED_NAME of [[PROV-N]].

Templates

Definition

A template is a PROV document that:

  • MUST contain exactly one bundle; statements outside this bundle are ignored by instantiation;
  • MAY contain [=variables=], in any position where PROV admits a qualified name, as specified in ;
  • MAY contain attributes of the tmpl: vocabulary ().

A template is a PROV document: it MAY be written in any serialization of PROV, among which PROV-N [[PROV-N]], PROV-JSONLD [[PROV-JSONLD]], PROV-JSON [[PROV-JSON]], PROV-XML [[PROV-XML]] and PROV-O [[PROV-O]]. Every tool that reads, converts or validates PROV applies to templates. 

document
  prefix var <http://openprovenance.org/var#>
  prefix vargen <http://openprovenance.org/vargen#>

  bundle vargen:b
    agent(var:a)
    entity(var:b)
    wasAttributedTo(var:b, var:a)
  endBundle
endDocument

Variables

A variable is a qualified name whose namespace is var: (http://openprovenance.org/var#) or vargen: (http://openprovenance.org/vargen#). The local part of a variable is its variable name; the bindings refer to variables by name.

  • A var variable, in the var: namespace, is replaced by its value. If it is unbound, the position it occupies is left empty, or the statement is left out, according to [[PROV-TEMPLATE-ALGORITHMS]].
  • A vargen variable, in the vargen: namespace, is replaced by its value if it is bound; if it is unbound, instantiation generates a fresh qualified name for it, in the uuid: namespace (urn:uuid:), the same for all its occurrences in one instantiation. A vargen variable MUST NOT be bound to more than one value.

A variable name SHOULD match the regular expression ^[^:\[\]()/\\,\-]+$ and MUST NOT be id, in any case: the bindings JSON Schema () rejects other names, and code generated from templates uses variable names as identifiers.

Positions of variables

The positions of a statement are those of its PROV-N form [[PROV-N]]: an optional identifier, then positional arguments, then, for some statements, a time, then attributes. Variables are classified by the position in which they occur.

  • A group variable occurs in the identifier position of a statement or in one of its positional arguments that precede the time: the identifier of an entity, activity or agent; the identifier of a relation; an influencer or influencee; a secondary argument such as the plan of an association, the activity of a delegation or of a derivation, the generation and usage of a derivation. A statement is instantiated once for each combination of the values of its group variables, as specified in [[PROV-TEMPLATE-ALGORITHMS]].
  • An attribute variable occurs as the value of an attribute, as in [prov:type = 'var:t'], or as the name of an attribute, as in [var:p = 'var:v']. An attribute variable does not multiply the statement it occurs in: each instance of the statement takes its own entry of the attribute variable's values.
  • A bundle variable is the identifier of the template's bundle. It is bound to a single value.

A variable MUST NOT be both a group variable and an attribute variable in the same template. A bundle variable MAY also be a group variable.

ProvToolbox does not check that a variable is not both a group variable and an attribute variable. The distinction was named "group variable" and "statement-level variable" in [[PROV-TEMPLATE-2014]].

Times cannot be variables, since PROV requires a time to be an xsd:dateTime. Likewise, a label must be a string. Values in such positions are given by the syntax-constrained attributes of the tmpl: vocabulary.

An attribute whose name is a variable is paired with its value: the i-th name bound to the name variable is paired with the i-th value bound to the value variable. This lets a template leave room for attributes that are only known when the template is used: 

entity(var:file, [prov:type = 'fs:DataFile', var:oprops = 'var:ovalues'])

The tmpl: vocabulary

The template vocabulary, in the namespace http://openprovenance.org/ns/tmpl#, defines attributes reserved for templates. In a template, the value of each of these attributes is a variable. Every tmpl: attribute is consumed by instantiation: none appears in an instantiated document, except tmpl:order when it is requested. The vocabulary is published as an RDF vocabulary [[TMPL-VOCAB]].

AttributeAllowed onMeaning
tmpl:labelany statement The statement is given a prov:label for each value of the variable, which MUST be bound to xsd:string values.
tmpl:timeusage, generation, invalidation, start, end The statement's time is the variable's value, which MUST be a single xsd:dateTime.
tmpl:startTimeactivity The activity's start time is the variable's value, a single xsd:dateTime.
tmpl:endTimeactivity The activity's end time is the variable's value, a single xsd:dateTime.
tmpl:ifany statement The statement is instantiated only if the variable is bound. A variable bound to a sequence of values counts as bound.
tmpl:notifany statement The statement is instantiated only if the variable is not bound; the complement of tmpl:if.
tmpl:IDa relation without identifier The relation's identifier is the variable's value, a qualified name. Ignored when the relation already has an identifier, or when the value is not a qualified name.
tmpl:linkeda statement whose identifier is a variable Names another variable, which changes value in step with the statement's identifier (). The link is symmetric. The named variable is not a free variable of the statement.
tmpl:order(output only) MAY be written by a processor, on request, on each instantiated statement: the index of the combination of values that produced it, such as "[1, 0]". It MUST NOT occur in a template.

The names tmpl:activity and tmpl:activityType are reserved for the template compiler ().

Where ProvToolbox's interpreter currently differs from the vocabulary:

  • tmpl:if and tmpl:notif are not implemented by the interpreter: a statement carrying them is instantiated in any case, and a bound tmpl:if is kept in the output. The template compiler implements tmpl:if, as a test of the value's truth, for invalidations and qualified memberships only.
  • A tmpl:time variable bound to several values gives the statement the last value; the vocabulary says such a binding is ignored.
  • tmpl:ID is kept in the output when it cannot be applied.
  • tmpl:order is not part of the published vocabulary [[TMPL-VOCAB]].

Linked variables

By default, the group variables of a statement change value independently, and the statement is instantiated for every combination of their values. Two variables are linked if a statement whose identifier is one of them carries a tmpl:linked attribute whose value is the other, or if the bindings declare the link (); the relation is symmetric and transitive. Linked variables change value in step: the i-th value of one goes with the i-th value of the other. Linked variables MUST be bound to the same number of values. 

entity(var:input)
entity(var:output, [tmpl:linked = 'var:input'])
wasDerivedFrom(var:output, var:input)

Templates generated from templates

Instantiation with bindings whose values are themselves variables produces a template: binding var:input to var:file renames a variable, and binding var:type to fs:DataFile specialises a template. When the value of a tmpl:label, tmpl:time, tmpl:startTime or tmpl:endTime variable is a variable, the attribute is kept, with the new variable as value. The template library [[PROV-TEMPLATE-LIBRARY]] derives most of its templates in this way, and by merge.

Bindings

Bindings

A set of bindings associates variables with values. A variable associated with a value is bound; otherwise it is unbound.

  • A group variable is bound to a sequence of qualified names; the statements using it are instantiated once for each.
  • An attribute variable is bound to a sequence of entries, one per instance of the statement in which it occurs, in the order of [[PROV-TEMPLATE-ALGORITHMS]]; each entry is a sequence of values, since an attribute may occur zero, one or several times in a statement. A value is a qualified name or a typed literal.
  • A bundle variable and a vargen variable are bound to a single qualified name.

JSON representation

A set of bindings is represented by a JSON object [[RFC8259]] with the following members.

MemberRequiredValue
varyesAn object mapping each bound variable name of the var: namespace to its values (below).
contextyesAn object mapping each prefix used in the values to its namespace IRI.
vargennoAn object mapping variable names of the vargen: namespace to a sequence of one qualified name.
linkednoAn object mapping a variable name to the name of a variable it is linked with.
templatenoThe identifier of the template the bindings are for, or null.
@documentationnoA description, or null.

The values of a variable are a JSON array, or null for an unbound variable.

  • A qualified name is written {"@id": "prefix:local"}. The prefix MUST be declared in context, except uuid, which denotes urn:uuid: when not declared.
  • A literal is written {"@value": "lexical form", "@type": "xsd:..."}; without @type, it is an xsd:string. A language-tagged string is written {"@value": "...", "@language": "en"}.
  • The values of a group variable are an array of qualified names. The values of an attribute variable are an array of entries, each an array of values. 
{
  "context": { "ex": "http://example.org/" },
  "var": {
    "a": [{"@id": "ex:ag1"}, {"@id": "ex:ag2"}],
    "b": [{"@id": "ex:en1"}, {"@id": "ex:en2"}, {"@id": "ex:en3"}],
    "c": [[{"@id": "ex:t1"}], [{"@id": "ex:t2a"}, {"@id": "ex:t2b"}], [{"@id": "ex:t3"}],
          [{"@id": "ex:t4"}], [{"@id": "ex:t5a"}, {"@id": "ex:t5b"}, {"@id": "ex:t5c"}], [{"@id": "ex:t6"}]]
  }
}

The values in a bindings file MAY contain placeholders ${name}, which a template transformation file replaces by the values of its variable maps before the bindings are read ().

  • ProvToolbox also accepts an entry of an attribute variable written as a single value rather than an array of one value, which the JSON Schema rejects.
  • ProvToolbox reads a language tag from @lang, the JSON Schema from @language (the JSON-LD keyword); the interpreter then ignores it.
  • The JSON Schema admits the types xsd:string, xsd:int, xsd:float, xsd:boolean and xsd:dateTime; the interpreter supports only xsd:string, xsd:int and xsd:boolean as values of ordinary attributes, and xsd:dateTime for the time attributes.
  • A value written as a full IRI rather than a qualified name is not supported.

Bindings schemas

      

        A bindings schema describes the variables of a template: for each
        variable, the kind of its values, their type, its documentation, an example, and whether an application
        supplies it or instantiation produces it. It is the contract between an application and a template, used to
        check bindings, to document templates, and to generate code (). In the
        template library, bindings schemas are also called compact bindings, and are found under
        cbindings/.
      

      
A bindings schema is a JSON object with the members of a set of bindings (), in which:

      
    
        
  • var maps each variable name to a description instead of values;
    • 
        
  • template identifies the template described;
    • 
        
  • @documentation describes the template.
    • 
      

      

        A group variable is described by an array of one object with the member @id; an attribute
        variable by an array of one array of one object with the member @value. The value of
        @id is a pattern prefix:*, standing for any qualified name in that namespace; the
        value of @value is *, standing for any literal. The other members are:
      

      

        
MemberOnValue

        
          
@typebothThe type of the values: xsd:string, xsd:int, xsd:float, xsd:boolean, xsd:dateTime. For a group variable, the type of the local part.

          
@documentationbothWhat the variable stands for.

          
@examplarbothAn example value.

          
@inputbothcompulsory, optional or false: whether, and how, the application supplies the value.

          
@outputbothtrue or false: whether the value is produced, for instance a generated identifier.

          
@sql.tablegroup variableThe table in which values are stored, for code generating SQL.

          
@sql.typeattribute variableThe SQL type of the values, such as timestamptz or nonNullableTEXT.

          
@transientattribute variabletrue, false or a method name: the value is never persisted, or kept only where the method says ().

          
@pseudonymbothA method name: the value arrives pseudonymised, in the method's form ().

          
@inJsonattribute variableThe name of a text variable of the template, the carrier: the value is encoded under a key of the JSON object that variable holds ().

          
@inJson.keyattribute variableThe key in the carrier, when it differs from the variable's name ().

          
@performativeattribute variablerequest or reply: whose content the value is, the caller's or the service's ().

        
      

      

        The order of the members of var is significant: it is the order of the fields of the records
        generated from the bindings schema. A bindings schema MUST validate against the JSON Schema of
        .
      

      

      

        The template compiler reads further members that the JSON Schema rejects: on a group variable
        @role, @escape, @semantic.type, @unique,
        @sql.new.inputs, @sql.also.outputs; on an attribute variable

Data-protection annotations

        

          Two members of a bindings schema let a template declare how the values of a variable that refers to a person
          are kept, so that a provenance store built from templates holds references to people, never their names: a
          name is resolved, when shown, from the system of record for people, and no name-to-reference mapping is kept.
        

        
    
          
  • @transient: the value exists while the template is filled in, and is never persisted, or kept
            only where its method says. true stands for the default method pt:drop;
            false for no annotation. A transient attribute variable is left unbound, so that the attribute
            is absent from the expanded document, as for any unbound attribute variable
            ([[PROV-TEMPLATE-ALGORITHMS]]). A name variable MUST NOT be transient: unbound, it would suppress its node.
    • 
          
  • @pseudonym: the value arrives already pseudonymised. Its method states the form a valid value
            takes, and the system readers resolve it against.
    • 
        

        

          Both annotations apply only to a variable whose value an application supplies: @input
          compulsory or optional, not an @output. A variable can't carry both. A
          method is a name, namespaced: a name without prefix stands for pt:, the prefix reserved for the
          methods of ProvToolbox; any other prefix belongs to whoever defines the method.
        

        

          
MethodKindMeaning

          
            
pt:droptransientKept nowhere: no column, no insert parameter, no log field value, no expanded attribute.

            
pt:local-logtransientKept in the caller's own log only, never in a store or an expanded document.

            
pt:ext-refpseudonymThe identifier of an external system that is the system of record (an ERP, an HR system, an identity realm), ^[a-z][a-z0-9_.-]*:[A-Za-z0-9_./-]+$, e.g. hr:person/4711.

            
pt:inline-refspseudonymFree text in which people appear only as references ⟨person ext-ref⟩, ^([^⟨⟩]|⟨person [a-z][a-z0-9_.-]*:[A-Za-z0-9_./-]+⟩)*$.

            
pt:keyed-hashpseudonymAn HMAC-SHA256 with a tenant key, prefixed by the key's identifier, ^[a-z0-9_-]+:[0-9a-f]{64}$. Destroying the key erases the tenant.

          
        

        

          A pseudonym method's form is a regular expression, anchored (^...$) and limited to what Java,
          Python, JavaScript, Rust and PostgreSQL read alike: character classes, {n}, *,
          +, ?, |; no \d, \w, \s, no
          (?...). A form check recognises a clear value by its shape, not its meaning.
        

        

          The annotations of a bindings schema state its author's intent. An application that uses a template library
          decides, from its own configuration, whether to honour, ignore or change them, and may define further methods
          ().
        

      


      

        
In-JSON values

        

          A template used for many kinds of act often keeps what differs from one kind to the next in a text variable
          that holds a JSON object, because adding a key there changes no table and no record. The price is that
          nothing declares the keys. Two members of a bindings schema declare some of them.
        

        

          A variable that carries @inJson is an in-JSON value. Its value is the value of a key
          of the JSON object held by another variable of the template, its carrier, named by
          @inJson. The key is the name of the variable, or @inJson.key when that member is
          present: one key may appear in two carriers of a template, which two variables of one name could not.
        

        
"priceBefore": [[{ "@value": "*", "@type": "xsd:double",
                   "@documentation": "The line's unit price before the act",
                   "@input": "optional", "@inJson": "pattributes" }]]

        

          An in-JSON value is not a variable of the template's graph: nothing in the template refers to it, and the
          bindings by which the template is instantiated never name it. A processor that reads a bindings schema
          takes the in-JSON values out of the template's variables, which are the ordinary ones: the records, tables and
          builders generated for a template are those it would have without them. Only its documentation and the
          descriptions of its records mention them.
        

        
A bindings schema MUST NOT:

        
    
          
  • put @inJson on a group variable, or @inJson.key without @inJson;
    • 
          
  • name as a carrier a variable that is not a value variable of the template, whose @type is
            neither xsd:string nor json, or that is itself an in-JSON value;
    • 
          
  • give an in-JSON value a type other than xsd:int, xsd:long, xsd:string,
            xsd:boolean, xsd:float, xsd:double, xsd:dateTime,
            xsd:date or json;
    • 
          
  • declare one key twice in one carrier;
    • 
          
  • combine @inJson with @sql.type, @sql.foreign, @unique,
            @escape, @output, @transient or @pseudonym. An in-JSON
            value is no column and no log field, so these have nothing to apply to; the annotations of its carrier
            cover the whole content of the carrier.
    • 
        

        

          The JSON Schema of  restricts @type to
          xsd:string, xsd:int, xsd:float, xsd:boolean and
          xsd:dateTime, so it rejects an in-JSON value, or any variable, of type xsd:double,
          xsd:long, xsd:date or json, which the template compiler reads. The
          types listed above are the compiler's. Either the schema or this list should change.
        

        

          A carrier is open. The in-JSON values declare some of the keys of a carrier, never all of
          them, and nothing closes it: a key nobody declared is expected, and software that reads and writes a carrier
          through its declaration MUST accept it, keep it and write it back.
        

        

          The text of a value. Software that writes the carrier does so in one way, so that the same
          values give the same text from any language: no space is written between tokens; an xsd:int or
          xsd:long is a JSON integer; an xsd:double is written by the number rule of
          [[RFC8785]] (5.0 is written 5), an xsd:float by the same rule with the
          shortest digits that read back as that float, and neither may be NaN or infinite; an xsd:boolean is
          true or false; an xsd:string, xsd:date and
          xsd:dateTime are JSON strings; a value of type json is the JSON it holds, nested in
          the carrier, not a string containing JSON. The members of the object are the declared keys that have a value,
          in the order of the bindings schema, followed by the other keys, each in the order it was given. (This is the
          one departure from [[RFC8785]], which sorts the members.) A value that is absent is not written.
        

      


      

        
Performatives

        

          A record of a request that a program served holds values from three hands: what the caller gave, what the service
          knew before it acted, and what became of the request. A bindings schema does not say which. The member
          @performative says it, for the values of the first and the last kind. A
          performative is the kind of act a message performs; here it names the two messages of one exchange,
          the request and the reply.
        

        
    
          
  • "request": the value is content of the request: the caller gives it.
    • 
          
  • "reply": the value is content of the reply: the service returns it.
    • 
          
  • Absent: neither. The value is the service's own.
    • 
        

        
"unitPrice": [[{ "@value": "*", "@type": "xsd:double", "@input": "optional",
                 "@inJson": "attributes", "@performative": "request" }]],
"outcome":   [[{ "@value": "*", "@type": "xsd:string", "@input": "compulsory",
                 "@performative": "reply" }]]

        

          The annotation is allowed on an ordinary value and on an in-JSON value (), one
          performative per value. A bindings schema MUST NOT put it on a group variable (a caller gives names, and the
          service finds the nodes), on an output (the store mints it), on a value that is no input of the template, on a
          carrier that holds in-JSON values (each of its values says its own), or with a word other than the two.
        

        

          The annotation changes nothing a template generates for its own records. It states which values a
          generated request and reply carry (), and the documentation, the JSON Schema
          and the Turtle description of the template say it. It does not mean that a reply follows a request, and the
          reply is not one act: whether it agrees, refuses or fails is said by a value inside it, which is any other value.
        

      

    


    

      
Template indexes

      

        A template index is a JSON file, named index.json, in a directory of templates. It maps
        each template identifier to the files, relative to the directory, that hold the template in each format.
        The formats are provn, jsonld, png and svg. A template
        identifier is a fully qualified name, such as org.openprovenance.templates.fs.FileTransforming,
        or the path of an output of a template transformation file without extension. An index MUST validate
        against the JSON Schema template-index-schema.json.
      

      

      

        A template processor that resolves an identifier in an index prefers the formats jsonld, then
        provn. The index that a template transformation file writes for its outputs also records,
        under hasProvenance, the record of the task that produced each output.
      

      
The written index uses the members qualifiedPng, qualifiedSvg and hasProvenance, which the index JSON Schema does not list.

    


    

      
Template transformation files

      

        A template transformation file (TTF) is a JSON file that lists
        tasks performed on templates: instantiating a template with bindings, or merging templates or documents.
        Executed in sequence, the tasks build a collection of templates, or of documents, from their sources; the
        outputs of a task can be the inputs of the next.

          An instantiate task has, in addition, the required members template, a template
          identifier, and bindings, the name of a bindings file found in bindings_path. It
          instantiates the template with the bindings. A merge task has, in addition, the required member
          inputs, an array of at least one template identifier. It merges the inputs, in order, as
          specified in [[PROV-TEMPLATE-ALGORITHMS]].

Resolution of paths

        
A template transformation file is executed with an input base directory and an output base directory.

        
    
          
  • An entry of template_path or variableMaps that starts with . is relative to the directory of the template transformation file.
    • 
          
  • An entry of template_path or bindings_path that starts with neither / nor . is relative to the input base directory.
    • 
          
  • output_dir is relative to the output base directory.
    • 
          
  • A template identifier is looked up in the template index of each directory of the task's template_path, then of the file's, then, if addOutputDirToInputPath is true, of the output directory.
    • 
          
  • Each output is added to the template index of output_dir, under output and, if present, outputFullyQualifiedName.
    • 
        

      


      

        
Schema check

        

          The value of schemaCheck selects the version of the PROV-JSONLD JSON Schema [[PROV-JSONLD]]
          against which each jsonld output is validated. It is none (the default: no
          check), default (the version the processor writes), or a date naming a version of the
          schema, such as 2026-10-14. The suffix -qn, as in default-qn,
          selects the strict variant of the schema, which also checks the syntax of qualified names. An output that
          fails its schema check fails the execution.
        

      


      

        
Provenance of the tasks

        

          A task with hasProvenance records what it did, as compact records of the template-management
          templates of the library ([[PROV-TEMPLATE-LIBRARY]], family ptm), one line per output format,
          in CSV. An instantiate task writes ptm_instantiating records, a merge task
          ptm_merging records, one for each input after the first, paired with the first.
        

        

          
RecordFields, in order

          
            
ptm_instantiatingdocument, provenance, template, bindings, agent, instantiating, email, time

            
ptm_mergingdocument, provenance, template1, template2, agent, merging, email, time

          
        

        
Templates and documents are named by their path relative to their template directory, bindings by their path relative to the input base directory, so that the records of several tasks connect: the output of one is the template of another.

The template compiler

        

          The template compiler generates, from templates and their bindings schemas, code by which an application
          produces provenance without building PROV itself. Its input is a catalogue, a JSON file
          listing templates, each with its identifier, its fully qualified name, its package and its bindings schema
          (cbindings); a composite entry (consistsOf, sharing) combines
          several instances of a template that share some variables; a subtype entry (subtype) describes
          a kind of record of a simple template (). For each template it generates:
        

        
    
          
  • beans and builders, in Java, Python, JavaScript and Rust, with one field per variable of the bindings schema, in order;
    • 
          
  • a compact record of the bindings, one line of CSV whose first field names the template, which an application can log cheaply;
    • 
          
  • SQL tables and functions to store records;
    • 
          
  • a JSON Schema and HTML documentation of the records;
    • 
          
  • the code by which provconvert -log2prov turns a log of records back into PROV, by instantiating each record's template.
    • 
        

        

          A catalogue may name a privacy policy (member privacy), by which an application decides the
          data-protection annotations () of the templates it compiles, without copying
          their library. The policy defines methods (methods: a kind; for a transient method
          the places it keeps a value in, among store, log,
          expansion; for a pseudonym method its pattern), which may redefine a
          pt: method under its name but not add one; and it decides, per scope (*,
          method:m, template:fqn,
          variable:fqn#var, the most specific winning), to honour an annotation,
          ignore it, or replace it, a replacement at variable scope also adding one a library didn't declare. Every
          decision other than honour carries a reason.
        

        

          Every method is resolved when the code is generated, and its meaning is then fixed: the generated SQL checks a
          pseudonymised column inline, in a constraint named by the digest of the method's definition; the generated
          client checks the value before writing it, in Java, Python and JavaScript (a catalogue that generates Rust
          is warned that the Rust client doesn't); and a privacy register, written beside the documentation, records
          for each annotated variable what was declared, what is in effect, who decided and why, and the digest. A
          template whose annotations are all ignored generates the same code as one without any.
        

        

          The generated client refuses a value not in its method's form without echoing it. A writer that bypasses the
          client is refused by the database constraint, whose error may repeat the row, the clear value included
          (PostgreSQL: Failing row contains (…)), to that writer and to the server log. A store that holds
          references to people should therefore set log_error_verbosity = terse, and only the generated
          client should write to it.
        


        

          
Subtypes

          

            A simple template serves many kinds of record when it keeps what differs in the carrier of its in-JSON
            values (). A subtype names one such kind: a general template, a
            simple template, with some of its inputs given a constant and a stated set of its in-JSON values. A record
            of a subtype is a record of the general template, in the same table and by the same insert
            function; the subtype adds nothing to the server side (no table, no builder, no entry in the catalogue's
            dispatch, no reader for -log2prov), and a store that loads the library sees the general template
            only. What a subtype generates is for the client: a typed bean, and conversions from it to the general
            template's input bean and back.
          

          
A subtype is an entry of the catalogue's templates, with @type subtype:

          
{ "@type": "subtype",
  "name": "repricing_rfq_line",
  "fullyQualifiedName": "com.example.actions.RepricingRfqLine",
  "package": "com.example.actions",
  "refines": "com.example.actions.UserInteracting",
  "fixed":   { "atype": "ex:RepricingRfqLine" },
  "carries": { "unitPrice": "required", "note": "optional" } }

          
    
            
  • name, fullyQualifiedName, package: as for any entry (the typed bean, the request and the reply are generated in this package); the name and the
              fully qualified name are not those of another entry.
    • 
            
  • refines: the fully qualified name of a simple template of the same catalogue.
    • 
            
  • fixed: for each variable named, the constant it has in every record of the subtype. The
              variable MUST be an input of the general template, not an output, a carrier or an in-JSON value, and the
              constant MUST fit its type; the constant of a node variable is the node's local part, a text without prefix. Two subtypes of one template MUST NOT fix the same values: a
              record of the general template could not tell them apart.
    • 
            
  • carries: for each in-JSON value of the general template the subtype has, required
              or optional. The carrier of each MUST be an input of the general template.
    • 
          

          

            The compiler refuses a subtype that breaks one of these, naming the subtype and what is wrong, and a
            catalogue with a subtype that is not an integrator catalogue ("integrator": true), since the
            typed bean converts to the input bean that only an integrator catalogue generates. A catalogue without
            subtypes, and without in-JSON values, generates exactly what it would without this section.
          


          

            
Typed beans

            

              For each subtype the compiler generates a class, from the same description for Java, Python and JavaScript
              (it is a PAST class, like the beans of the other templates, and no text of one language). Named as the
              input bean of the general template is, from the subtype's name, and in the subtype's package, it has:
            

            
    
              
  • constants isA, the subtype's fully qualified name, and refines, the general
                template's;
    • 
              
  • a field for each input of the general template, except the fixed ones and the carriers the subtype
                carries values in;
    • 
              
  • a field for each carried value, of the type of its @type;
    • 
              
  • for each carrier the subtype carries values in, a map of the other keys of the carrier
                (carrierOther), whose values are JSON values. It is how a key nobody declared
                reaches the record ();
    • 
              
  • toGeneral(), which returns the general template's input bean: it copies the ordinary
                fields, assigns the fixed constants, refuses a required value that is absent, and writes each carrier as
                the JSON text of , declared keys first and then the other keys, refusing an
                other key that is a declared one;
    • 
              
  • the static fromGeneral(general), which refuses an input bean whose fixed variables do not
                hold the subtype's constants, copies the ordinary fields, reads each carrier and gives each carried
                field its key's value, with every other key in the map of other keys, and applies the check of required
                values.
    • 
            

            

              A carrier in which the subtype carries nothing stays an ordinary field, passed through as it is. There is
              no typed bean for the outputs: a record of a subtype returns what the general template's returns.
              Converting a typed bean with toGeneral and back with fromGeneral gives back the
              bean, other keys included; converting a general bean with fromGeneral and back gives back the
              same JSON object in each carrier, but not always the same text, since the declared keys are written first.
            

            

              When the catalogue has a subtype, it also generates one class, Subtypes, which for each general
              template that has subtypes tells, from an input bean, the subtype whose fixed values the bean holds (the
              one with the most fixed values first), and gives its typed bean.
            

            

              Writing and reading JSON text is not in PAST: the generated code calls one small class, of the same name and
              behaviour in each language (org.openprovenance.prov.utils.JsonText, in ProvToolbox's
              prov-model for Java, a candy of the JavaScript build, and a module of the Python template
              library), that the client project depends on only when its catalogue has a subtype. Every language runs
              the same table of values and the text each must give, which is what makes the text one.
            

            

              Three gaps in what ProvToolbox generates today. (1) In Rust the typed bean has its fields and no
              conversions, nor the Subtypes class: Rust has no mapping for a static call to the runtime
              class. (2) In Python, an optional value that is absent is written as 0, not as absent, by
              the Python bean generator generally; the conversions are right for present values only. (3) The JavaScript
              build the compiler generates does not yet transpile anything, so the JavaScript typed bean is emitted but
              not built into a client by the compiler. The runtime class is tested in all three languages against the
              shared table.
            

          


          

            
Requests and replies

            

              The typed bean holds every input of a record, so a JSON reader that fills it from the body of a request sets
              whatever the body names, the service's own values included. When values have a performative
              (), the compiler generates two more classes for a subtype, in the package of its
              typed bean: NameRequest, when the subtype has a value of the request, and
              NameReply, when it has a value of the reply. A subtype has a value when it is an
              ordinary input it does not fix, or an in-JSON value it carries.
            

            
    
              
  • Each has one field for each of its values, of the type the value has in the typed bean, and no other
                field: a body that names a value of the service cannot set it.
    • 
              
  • into(typed) copies the fields into the typed bean it is given, and returns it; it touches
                no other field. The static of(typed) makes the class from a typed bean. They copy fields and
                call no runtime class, and check nothing: the check of required values stays in
                toGeneral(), through which every record passes.
    • 
              
  • The request has the map of other keys (carrierOther) of each carrier the subtype
                carries values in, when every value the template declares in that carrier is a value of the request, so
                that a key nobody declared can reach the record from the caller. into copies the map when it
                is present. A carrier that also holds a value of the reply, or one of the service's own, has none in the
                request. The reply has no map.
    • 
            

            

              The JSON Schema of the catalogue has a definition for each, subtypeRequest and
              subtypeReply, with the values typed, the required ones required and no other property,
              and without isA: an application can publish the first as the schema of its request body. The
              documentation lists the values of a subtype by whose content they are. The Turtle file declares the term
              tpl:performative when a value has one and gives it, "request" or
              "reply", to the property of the value. An ordinary value that has a performative has a property,
              named like those of in-JSON values and without tpl:inJson, and its template is then described
              too.
            

            

              As for typed beans: in Rust the classes have their fields and no into or of, because
              the Rust generator writes the assignment of one bean's field to another as Some(x.to_string()) or
              Some(x), which does not compile for the optional field a bean has. In Python the test for an
              absent map of other keys is written != 0, so into copies None over the
              typed bean's own map.
            

          


          

            
Descriptions

            
    
              
  • The documentation lists, under each general template, the keys of its carriers with
                their in-JSON values, and its subtypes, each with what it fixes and carries.
    • 
              
  • The JSON Schema of the catalogue has, for each subtype, a definition of its typed bean:
                its own isA, the inputs it keeps, each carried value as a typed property (the required ones
                required), and for each carrier an object with free members for the other keys. The general template's
                schema is unchanged: the carrier is a string there.
    • 
              
  • The Turtle file, when the catalogue names one (members turtle, the file,
                and turtleNamespace, the namespace of its terms, which is then required), says what the
                compiler knows of the subtypes in the following vocabulary, tpl:
                (http://openprovenance.org/ns/tpl#).
    • 
            

            

              
TermMeaning

              
                
a template that keeps in-JSON values or has subtypesan owl:Class, named from the template's name; tpl:fullyQualifiedName gives its fully qualified name.

                
an in-JSON valuean owl:DatatypeProperty, named template-value so that two templates may use a name, with rdfs:domain the template, rdfs:range its type (rdf:JSON for json), tpl:inJson its carrier and, when it differs from the name, tpl:key.

                
a subtypean owl:Class, named from the subtype's name, rdfs:subClassOf its general template: every record of the subtype is a record of the template.

                
tpl:fixesfrom a subtype, a node with tpl:variable and tpl:value: an input the subtype gives a constant.

                
tpl:requires, tpl:mayCarryfrom a subtype, an in-JSON value every record of it gives, or may give; a carrier is open, so other keys are allowed.

              
            

            

              An application's own description of its kinds of record (their labels and comments) remains the
              application's to write: the file states what the compiler knows and has checked.
            

          

        


        

          
Flows

          

            A request has a request class, a user bean (the typed bean of a user subtype) and a reply class; the backend's
            record has a typed bean of its own, a subtype of the template the store loads. A flow connects them: one
            class of three steps, ask (the request becomes the user bean), record (the user bean and the
            records that made things as they stood become the backend's bean) and answer (what the store made becomes
            the reply), with a reply for a refused and for a failed request. Its point is that every input of those beans has
            one stated origin, so that the backend's record can be shown faithful to what the person asked: a
            value the person did not give cannot be passed off as asked.
          

          
A flow is an entry of the catalogue's templates, with @type flow:

          
{ "@type": "flow", "name": "repricing_flow",
  "fullyQualifiedName": "com.example.flows.RepricingFlow", "package": "com.example.flows",
  "from": "com.example.actions.Repricing", "to": "com.example.backend.LineChange",
  "stood": {
    "document": { "node": "document0", "madeBy": "document1", "addressed": "subject0" },
    "line":     { "node": "part0", "madeBy": "part1", "identity": { "user": "line", "backend": "partLine" } } },
  "ask":    { "agent": { "supplied": "caller" }, "time": { "supplied": "clock" } },
  "record": { "agent": "asked", "time": "asked",
              "partLine": { "asked": "line", "as": "text" }, "priceUnit": { "asked": "unitPrice", "as": "text" },
              "priceBefore": { "carried": "line.partPriceUnit" },
              "atype": { "constant": "Repricing" }, "estimate": { "supplied": "estimate" },
              "attributesOther": "absent" },
  "carry":     { "line": "rest", "document": [ "items", "currency", "name1" ] },
  "carryOpen": { "pattributes": "line" },
  "reply": { "answer":  { "outcome": { "when": { "made": "document1" }, "is": "accepted", "otherwise": "failed" },
                          "result": { "recorded": "erpId1" }, "code": "absent" },
             "refused": { "outcome": { "constant": "refused" }, "code": { "argument": true }, "result": "absent" } } }

          
    
            
  • from, to: the user subtype and the backend subtype the flow connects, both of the catalogue.
    • 
            
  • stood: each thing that stood before, by a name of the flow's own, as the record that made it: the
              backend's input node it becomes (node), the output node of that record that made it
              (madeBy), optionally the user bean's node that must be the same node (addressed) and the user
              value and backend value that say which thing it is (identity), and optionally the subtype of that
              record (of). The document and the line are two records as soon as another line changed in between.
    • 
            
  • ask: the user bean's own values, the ones the request does not give and the reply does not return.
    • 
            
  • record: the backend's inputs not carried over. carry: from which stood thing the other
              values come, unchanged and by their own name, as an explicit list or "rest" (for at most one thing).
              carryOpen: for each carrier of the backend's bean, the stood thing whose other keys are carried; the
              act's are not, since a removal's reason would leak into the next reprice.
    • 
            
  • reply: for answer, refused and failed, how each value of the
              reply class is given.
    • 
          

          

            
KindThe value isWritten

            
              
AS ASKEDthe request's (through the user bean)"asked", {"asked": value, "as": "text"}

              
CHAINEDa node a previous record madestood

              
CARRIED OVERa previous record's, unchangedcarry, carryOpen, {"carried": "thing.value"}

              
CONSTANTthe same for every record of this kind of act{"constant": v}

              
SUPPLIEDthe application's to compute: a rule, not a copy{"supplied": rule}, {"argument": true}

              
AS MADEthe backend record's, given back to the caller{"recorded": value}, {"made": output}, {"when": ...}

            
          

          

            Every input is accounted for exactly once. An input of the backend's bean is a field of the typed bean
            of its subtype: the ordinary inputs the subtype does not fix, the carried in-JSON values, and the map of other keys of
            each carrier it carries values in. Each MUST be said once, by record, carry,
            carryOpen or as a stood node; a value deliberately left unset is said, "absent",
            and MUST NOT be compulsory. The same holds of the user bean's own values and of the reply's values in each reply
            block. The compiler refuses a flow that leaves one out or names one twice, that names what is no value or no node, a
            conversion it does not have, a rule used for two values, two stood things for one node, or a reply that says what the
            store made when nothing was recorded.
          

          

            It generates, for Java, Python and JavaScript, one class Flow with the static methods
            ask, record, answer, refused and failed, and, when
            the flow has a supplied value, one interface FlowRules with a method for each, which the
            application implements. A rule receives the beans in scope in its step (the user bean, the backend's bean so far and
            each stood thing's inputs and outputs), not strings picked out of them. Each assignment is preceded by a comment that
            names its kind and the value; record refuses, before anything is built, a previous record that is not of
            the line the request names, and a request that addresses another document than the one the previous record made.
            A number or a boolean given to a text value goes through the runtime class, JsonText.text, so that every
            language gives the same text; null stays null.
          

          

            The documentation lists each flow as a table, one row for each value: the kind and where it comes from. The Turtle
            file describes it with tpl:Flow, tpl:from and tpl:to and, for each value, a node
            tpl:origin with tpl:step, tpl:target, tpl:kind and
            tpl:source. A flow has no record, so the JSON Schema says nothing of it.
          

          

            Not generated for Rust, which has no mapping for the runtime class. A double has no trailing zeros: a price asked as
            2.50 is recorded as 2.5 until there is a decimal type. "rest" carries over every
            input the declaration does not say, from the stood thing, when that thing's bean has a value of that name, so a supplied
            value the declaration forgets is carried over without a refusal; the table in the documentation shows it.
            In Python an absent value is tested as != 0, and the generated JavaScript build transpiles nothing, as for
            the typed beans.
