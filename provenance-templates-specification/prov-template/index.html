A provenance template is a PROV document [[PROV-DM]] in which some identifiers, attributes and values are variables. A set of bindings associates values with the variables, and instantiation replaces the variables by their values to produce an ordinary PROV document. This document specifies the artefacts of the provenance template approach: templates, their variables and the tmpl: vocabulary; the JSON representation of bindings; bindings schemas, which describe the variables of a template; template indexes; and template transformation files, which automate the instantiation and merge of templates. It also describes, non-normatively, the command-line tools, the executables, the Maven plugin and the template compiler of ProvToolbox [[PROVTOOLBOX]] that process them. The algorithms are specified in [[PROV-TEMPLATE-ALGORITHMS]].

This is an unofficial draft, part of the PROV-TEMPLATE family of documents [[PROV-TEMPLATE-OVERVIEW]]. It has no official standing of any kind and does not represent the consensus of any standards organisation.

This document revises and extends PROV-TEMPLATE: A Template System for PROV Documents [[PROV-TEMPLATE-2014]], edited in 2014 by Danius Michaelides, Trung Dong Huynh and Luc Moreau. The definitions of templates and of the representation of bindings as PROV documents come from that draft; its algorithm is now in [[PROV-TEMPLATE-ALGORITHMS]]. lists the changes.

The JSON Schemas included in this document are copies of those distributed with ProvToolbox (branch development2_0, commit 95386ae29, 2026-10-16) and with the template library. Editor's notes mark where this document, the schemas and ProvToolbox currently disagree.

A template processor is software that instantiates templates with bindings, or merges templates or documents, according to this specification and [[PROV-TEMPLATE-ALGORITHMS]]. A template processor conforms to this specification if it accepts every conforming template, set of bindings and template transformation file, and processes them as specified.

Introduction

Provenance often follows patterns that repeat during the lifetime of an application. Provenance templates declare such patterns once, in PROV itself, with variables acting as placeholders for values; the pattern is instantiated many times, each time with a new set of bindings for the variables. The code that instruments the application only collects values, and the generation of provenance is left to instantiation [[PROV-TEMPLATE-TSE]]. [[PROV-TEMPLATE-OVERVIEW]] presents the approach and [[PROV-TEMPLATE-PRIMER]] introduces it through an example.

This document is organised as follows.

  • defines templates, their variables and the reserved tmpl: attributes.
  • defines bindings and their JSON representation.
  • defines bindings schemas.
  • defines template indexes, by which templates are found by identifier.
  • defines template transformation files.
  • , non-normative, describes the ProvToolbox tools that process these artefacts.

Conventions

Unless otherwise stated, examples use the PROV-N notation [[PROV-N]]. The term qualified name is used as in [[PROV-DM]], with the syntax of the production QUALIFIED_NAME of [[PROV-N]].

Templates

Definition

A template is a PROV document that:

  • MUST contain exactly one bundle; statements outside this bundle are ignored by instantiation;
  • MAY contain [=variables=], in any position where PROV admits a qualified name, as specified in ;
  • MAY contain attributes of the tmpl: vocabulary ().

A template is a PROV document: it MAY be written in any serialization of PROV, among which PROV-N [[PROV-N]], PROV-JSONLD [[PROV-JSONLD]], PROV-JSON [[PROV-JSON]], PROV-XML [[PROV-XML]] and PROV-O [[PROV-O]]. Every tool that reads, converts or validates PROV applies to templates. 

document
  prefix var <http://openprovenance.org/var#>
  prefix vargen <http://openprovenance.org/vargen#>

  bundle vargen:b
    agent(var:a)
    entity(var:b)
    wasAttributedTo(var:b, var:a)
  endBundle
endDocument

Variables

A variable is a qualified name whose namespace is var: (http://openprovenance.org/var#) or vargen: (http://openprovenance.org/vargen#). The local part of a variable is its variable name; the bindings refer to variables by name.

  • A var variable, in the var: namespace, is replaced by its value. If it is unbound, the position it occupies is left empty, or the statement is left out, according to [[PROV-TEMPLATE-ALGORITHMS]].
  • A vargen variable, in the vargen: namespace, is replaced by its value if it is bound; if it is unbound, instantiation generates a fresh qualified name for it, in the uuid: namespace (urn:uuid:), the same for all its occurrences in one instantiation. A vargen variable MUST NOT be bound to more than one value.

A variable name SHOULD match the regular expression ^[^:\[\]()/\\,\-]+$ and MUST NOT be id, in any case: the bindings JSON Schema () rejects other names, and code generated from templates uses variable names as identifiers.

Positions of variables

The positions of a statement are those of its PROV-N form [[PROV-N]]: an optional identifier, then positional arguments, then, for some statements, a time, then attributes. Variables are classified by the position in which they occur.

  • A group variable occurs in the identifier position of a statement or in one of its positional arguments that precede the time: the identifier of an entity, activity or agent; the identifier of a relation; an influencer or influencee; a secondary argument such as the plan of an association, the activity of a delegation or of a derivation, the generation and usage of a derivation. A statement is instantiated once for each combination of the values of its group variables, as specified in [[PROV-TEMPLATE-ALGORITHMS]].
  • An attribute variable occurs as the value of an attribute, as in [prov:type = 'var:t'], or as the name of an attribute, as in [var:p = 'var:v']. An attribute variable does not multiply the statement it occurs in: each instance of the statement takes its own entry of the attribute variable's values.
  • A bundle variable is the identifier of the template's bundle. It is bound to a single value.

A variable MUST NOT be both a group variable and an attribute variable in the same template. A bundle variable MAY also be a group variable.

ProvToolbox does not check that a variable is not both a group variable and an attribute variable. The distinction was named "group variable" and "statement-level variable" in [[PROV-TEMPLATE-2014]].

Times cannot be variables, since PROV requires a time to be an xsd:dateTime. Likewise, a label must be a string. Values in such positions are given by the syntax-constrained attributes of the tmpl: vocabulary.

An attribute whose name is a variable is paired with its value: the i-th name bound to the name variable is paired with the i-th value bound to the value variable. This lets a template leave room for attributes that are only known when the template is used: 

entity(var:file, [prov:type = 'fs:DataFile', var:oprops = 'var:ovalues'])

The tmpl: vocabulary

The template vocabulary, in the namespace http://openprovenance.org/ns/tmpl#, defines attributes reserved for templates. In a template, the value of each of these attributes is a variable. Every tmpl: attribute is consumed by instantiation: none appears in an instantiated document, except tmpl:order when it is requested. The vocabulary is published as an RDF vocabulary [[TMPL-VOCAB]].

AttributeAllowed onMeaning
tmpl:labelany statement The statement is given a prov:label for each value of the variable, which MUST be bound to xsd:string values.
tmpl:timeusage, generation, invalidation, start, end The statement's time is the variable's value, which MUST be a single xsd:dateTime.
tmpl:startTimeactivity The activity's start time is the variable's value, a single xsd:dateTime.
tmpl:endTimeactivity The activity's end time is the variable's value, a single xsd:dateTime.
tmpl:ifany statement The statement is instantiated only if the variable is bound. A variable bound to a sequence of values counts as bound.
tmpl:notifany statement The statement is instantiated only if the variable is not bound; the complement of tmpl:if.
tmpl:IDa relation without identifier The relation's identifier is the variable's value, a qualified name. Ignored when the relation already has an identifier, or when the value is not a qualified name.
tmpl:linkeda statement whose identifier is a variable Names another variable, which changes value in step with the statement's identifier (). The link is symmetric. The named variable is not a free variable of the statement.
tmpl:order(output only) Written by instantiation, on request, on each instantiated statement: the index of the combination of values that produced it, such as "[1, 0]". It MUST NOT occur in a template.

The names tmpl:activity and tmpl:activityType are reserved for the template compiler ().

Where ProvToolbox's interpreter currently differs from the vocabulary:

  • tmpl:if and tmpl:notif are not implemented by the interpreter: a statement carrying them is instantiated in any case, and a bound tmpl:if is kept in the output. The template compiler implements tmpl:if, as a test of the value's truth, for invalidations and qualified memberships only.
  • A tmpl:time variable bound to several values gives the statement the last value; the vocabulary says such a binding is ignored.
  • tmpl:ID is kept in the output when it cannot be applied.
  • tmpl:order is not part of the published vocabulary [[TMPL-VOCAB]].

Linked variables

By default, the group variables of a statement change value independently, and the statement is instantiated for every combination of their values. Two variables are linked if a statement whose identifier is one of them carries a tmpl:linked attribute whose value is the other, or if the bindings declare the link (); the relation is symmetric and transitive. Linked variables change value in step: the i-th value of one goes with the i-th value of the other. Linked variables MUST be bound to the same number of values. 

entity(var:input)
entity(var:output, [tmpl:linked = 'var:input'])
wasDerivedFrom(var:output, var:input)

Templates generated from templates

Instantiation with bindings whose values are themselves variables produces a template: binding var:input to var:file renames a variable, and binding var:type to fs:DataFile specialises a template. When the value of a tmpl:label, tmpl:time, tmpl:startTime or tmpl:endTime variable is a variable, the attribute is kept, with the new variable as value. The template library [[PROV-TEMPLATE-LIBRARY]] derives most of its templates in this way, and by merge.

Bindings

Bindings

A set of bindings associates variables with values. A variable associated with a value is bound; otherwise it is unbound.

  • A group variable is bound to a sequence of qualified names; the statements using it are instantiated once for each.
  • An attribute variable is bound to a sequence of entries, one per instance of the statement in which it occurs, in the order of [[PROV-TEMPLATE-ALGORITHMS]]; each entry is a sequence of values, since an attribute may occur zero, one or several times in a statement. A value is a qualified name or a typed literal.
  • A bundle variable and a vargen variable are bound to a single qualified name.

JSON representation

A set of bindings is represented by a JSON object [[RFC8259]] with the following members.

MemberRequiredValue
varyesAn object mapping each bound variable name of the var: namespace to its values (below).
contextyesAn object mapping each prefix used in the values to its namespace IRI.
vargennoAn object mapping variable names of the vargen: namespace to a sequence of one qualified name.
linkednoAn object mapping a variable name to the name of a variable it is linked with.
templatenoThe identifier of the template the bindings are for, or null.
@documentationnoA description, or null.

The values of a variable are a JSON array, or null for an unbound variable.

  • A qualified name is written {"@id": "prefix:local"}. The prefix MUST be declared in context, except uuid, which denotes urn:uuid: when not declared.
  • A literal is written {"@value": "lexical form", "@type": "xsd:..."}; without @type, it is an xsd:string. A language-tagged string is written {"@value": "...", "@language": "en"}.
  • The values of a group variable are an array of qualified names. The values of an attribute variable are an array of entries, each an array of values. 
{
  "context": { "ex": "http://example.org/" },
  "var": {
    "a": [{"@id": "ex:ag1"}, {"@id": "ex:ag2"}],
    "b": [{"@id": "ex:en1"}, {"@id": "ex:en2"}, {"@id": "ex:en3"}],
    "c": [[{"@id": "ex:t1"}], [{"@id": "ex:t2a"}, {"@id": "ex:t2b"}], [{"@id": "ex:t3"}],
          [{"@id": "ex:t4"}], [{"@id": "ex:t5a"}, {"@id": "ex:t5b"}, {"@id": "ex:t5c"}], [{"@id": "ex:t6"}]]
  }
}

The values in a bindings file MAY contain placeholders ${name}, which a template transformation file replaces by the values of its variable maps before the bindings are read ().

  • ProvToolbox also accepts an entry of an attribute variable written as a single value rather than an array of one value, which the JSON Schema rejects.
  • ProvToolbox reads a language tag from @lang, the JSON Schema from @language (the JSON-LD keyword); the interpreter then ignores it.
  • The JSON Schema admits the types xsd:string, xsd:int, xsd:float, xsd:boolean and xsd:dateTime; the interpreter supports only xsd:string, xsd:int and xsd:boolean as values of ordinary attributes, and xsd:dateTime for the time attributes.
  • A value written as a full IRI rather than a qualified name is not supported.

JSON Schema

A set of bindings MUST validate against the JSON Schema bindings-schema.json [[JSON-SCHEMA]], which also validates bindings schemas (). 


          
The schema does not list the member linked, which ProvToolbox accepts.

        

      


      

        
Bindings as PROV documents (deprecated)

        

          [[PROV-TEMPLATE-2014]] represented bindings as a PROV document, so as not to introduce a new syntax: each
          variable is an entity, and its values are attributes in the tmpl: namespace:
          tmpl:value_i for the i-th value of a group variable, tmpl:2dvalue_i_j for the
          j-th value of the i-th entry of an attribute variable. A later version used tmpl:binding_i.
          These representations are deprecated. ProvToolbox converts them (the bindings commands of
          provmanager) but no longer instantiates from them.
        

        
document
  prefix var <http://openprovenance.org/var#>
  prefix tmpl <http://openprovenance.org/tmpl#>
  prefix ex <http://example.org/>

  entity(var:a, [tmpl:value_0 = 'ex:ag1', tmpl:value_1 = 'ex:ag2'])
  entity(var:c, [tmpl:2dvalue_0_0 = 'ex:t1', tmpl:2dvalue_1_0 = 'ex:t2a', tmpl:2dvalue_1_1 = 'ex:t2b'])
endDocument

      

    


    

      
Bindings schemas

      

        A bindings schema describes the variables of a template: for each
        variable, the kind of its values, their type, its documentation, an example, and whether an application
        supplies it or instantiation produces it. It is the contract between an application and a template, used to
        check bindings, to document templates, and to generate code (). In the
        template library, bindings schemas are also called compact bindings, and are found under
        cbindings/.
      

      
A bindings schema is a JSON object with the members of a set of bindings (), in which:

      
    
        
  • var maps each variable name to a description instead of values;
    • 
        
  • template identifies the template described;
    • 
        
  • @documentation describes the template.
    • 
      

      

        A group variable is described by an array of one object with the member @id; an attribute
        variable by an array of one array of one object with the member @value. The value of
        @id is a pattern prefix:*, standing for any qualified name in that namespace; the
        value of @value is *, standing for any literal. The other members are:
      

      

        
MemberOnValue

        
          
@typebothThe type of the values: xsd:string, xsd:int, xsd:float, xsd:boolean, xsd:dateTime. For a group variable, the type of the local part.

          
@documentationbothWhat the variable stands for.

          
@examplarbothAn example value.

          
@inputbothcompulsory, optional or false: whether, and how, the application supplies the value.

          
@outputbothtrue or false: whether the value is produced, for instance a generated identifier.

          
@sql.tablegroup variableThe table in which values are stored, for code generating SQL.

          
@sql.typeattribute variableThe SQL type of the values, such as timestamptz or nonNullableTEXT.

        
      

      

        The order of the members of var is significant: it is the order of the fields of the records
        generated from the bindings schema. A bindings schema MUST validate against the JSON Schema of
        .
      

      

      

        The template compiler reads further members that the JSON Schema rejects: on a group variable
        @role, @escape, @semantic.type, @unique,
        @sql.new.inputs, @sql.also.outputs; on an attribute variable
        @sql.foreign, @unique, @escape; @output: "optional";
        and a top-level @return. Either the schema or this section should grow to cover them.
      

    


    

      
Template indexes

      

        A template index is a JSON file, named index.json, in a directory of templates. It maps
        each template identifier to the files, relative to the directory, that hold the template in each format.
        The formats are provn, jsonld, png and svg. A template
        identifier is a fully qualified name, such as org.openprovenance.templates.fs.FileTransforming,
        or the path of an output of a template transformation file without extension. An index MUST validate
        against the JSON Schema template-index-schema.json.
      

      

      

        A template processor that resolves an identifier in an index prefers the formats jsonld, then
        provn. The index that a template transformation file writes for its outputs also records,
        under hasProvenance, the record of the task that produced each output.
      

      
The written index uses the members qualifiedPng, qualifiedSvg and hasProvenance, which the index JSON Schema does not list.

    


    

      
Template transformation files

      

        A template transformation file (TTF) is a JSON file that lists
        tasks performed on templates: instantiating a template with bindings, or merging templates or documents.
        Executed in sequence, the tasks build a collection of templates, or of documents, from their sources; the
        outputs of a task can be the inputs of the next.
      


      

        
Structure

bindings_pathyesThe directories in which bindings files are looked up, in order.

            
output_diryesThe directory in which outputs, and their index, are written.

            
variableMapsyesJSON files, each an object mapping names to strings, that replace the placeholders ${name} of bindings files.

            
tasksyesThe tasks, at least one, each an instantiate task or a merge task.

          identifier, and bindings, the name of a bindings file found in bindings_path. It
          instantiates the template with the bindings. A merge task has, in addition, the required member
          inputs, an array of at least one template identifier. It merges the inputs, in order, as
          specified in [[PROV-TEMPLATE-ALGORITHMS]].

Resolution of paths

        
A template transformation file is executed with an input base directory and an output base directory.

        
    
          
  • An entry of template_path or variableMaps that starts with . is relative to the directory of the template transformation file.
    • 
          
  • An entry of template_path or bindings_path that starts with neither / nor . is relative to the input base directory.
    • 
          
  • output_dir is relative to the output base directory.
    • 
          
  • A template identifier is looked up in the template index of each directory of the task's template_path, then of the file's, then, if addOutputDirToInputPath is true, of the output directory.
    • 
          
  • Each output is added to the template index of output_dir, under output and, if present, outputFullyQualifiedName.
    • 
        

      


      

        
Schema check

        

          The value of schemaCheck selects the version of the PROV-JSONLD JSON Schema [[PROV-JSONLD]]
          against which each jsonld output is validated. It is none (the default: no
          check), default (the version the processor writes), or a date naming a version of the
          schema, such as 2026-10-14. The suffix -qn, as in default-qn,
          selects the strict variant of the schema, which also checks the syntax of qualified names. An output that
          fails its schema check fails the execution.
        

      


      

        
Provenance of the tasks

        

          A task with hasProvenance records what it did, as compact records of the template-management
          templates of the library ([[PROV-TEMPLATE-LIBRARY]], family ptm), one line per output format,
          in CSV. An instantiate task writes ptm_instantiating records, a merge task
          ptm_merging records, one for each input after the first, paired with the first.
        

        

          
RecordFields, in order

          
            
ptm_instantiatingdocument, provenance, template, bindings, agent, instantiating, email, time

            
ptm_mergingdocument, provenance, template1, template2, agent, merging, email, time

          
        

        
Templates and documents are named by their path relative to their template directory, bindings by their path relative to the input base directory, so that the records of several tasks connect: the output of one is the template of another.

        

      

    


    

      
Tools

      
This section describes the ProvToolbox [[PROVTOOLBOX]] tools that process the artefacts of this specification.


      

        
The command line: provconvert

        
provconvert converts between PROV formats and instantiates and merges templates.

        
provconvert -infile template.provn -bindings bindings.json -outfile document.provn

        

          
OptionEffect

          
            
-infile fileThe input: the template, when -bindings is given.

            
-outfile fileThe output, whose format is given by its extension (provn, jsonld, svg, …).

            
-bindings fileInstantiate the input with the given bindings; - reads them from standard input.

            
-bindver nThe version of the bindings; only 3, the JSON representation, the default, is supported.

            
-genorderWrite tmpl:order on instantiated statements.

            
-allexpandedInstantiate a statement only if all its variables are bound; the exit status is 7 if some were not.

            
-merge fileMerge the documents listed in the file, one per line, into the output; with -flatten, into a single bundle-less document.

            
-log2prov classTurn a log of compact records (-infile) into a PROV document, with the given generated initialiser class ().

            
-templatebuilder fileRun the template compiler on the given catalogue.

            
-templateLibrary pathsDirectories of templates, for the template compiler.

            
-inputBaseDir, -outputBaseDirBase directories of relative paths.

The template compiler

        

          The template compiler generates, from templates and their bindings schemas, code by which an application
          produces provenance without building PROV itself. Its input is a catalogue, a JSON file
          listing templates, each with its identifier, its fully qualified name, its package and its bindings schema
          (cbindings); a composite entry (consistsOf, sharing) combines
          several instances of a template that share some variables. For each template it generates:
        

        
    
          
  • beans and builders, in Java, Python, JavaScript and Rust, with one field per variable of the bindings schema, in order;
    • 
          
  • a compact record of the bindings, one line of CSV whose first field names the template, which an application can log cheaply;
    • 
          
  • SQL tables and functions to store records;
    • 
          
  • a JSON Schema and HTML documentation of the records;
    • 
          
  • the code by which provconvert -log2prov turns a log of records back into PROV, by instantiating each record's template.
    •
