The same patterns of provenance recur across applications: a file is transformed, an item is packed into a container, responsibility for a thing is handed over, an entity is examined. This document describes a library of provenance templates [[PROV-TEMPLATE]] that captures such patterns, maintained at openprovenance.org [[TEMPLATE-LIBRARY-SITE]]. It explains how templates in the library are identified, organised, documented and published; how most of them are derived from a small number of primitive templates by instantiation and merge; and it lists the families of templates the library contains.

This is an unofficial draft, part of the PROV-TEMPLATE family of documents [[PROV-TEMPLATE-OVERVIEW]]. It is not normative. It describes the library as of 2026-10-16 (commit c99f358 of [[TEMPLATE-LIBRARY-SOURCE]]); the library is a living collection, and its own index and pages are authoritative for its current content. The library is the subject of a chapter of [[PTM-BOOK]].

Introduction

A template is worth more when it is shared. A shared template carries a design decision about how a kind of event is described in PROV — which nodes, which relations, which attributes — and every application that reuses it produces provenance of the same shape, which can be queried, compared and explained in the same way. A template library is a published collection of such templates, each with a stable identifier, a bindings schema [[PROV-TEMPLATE]] describing its variables, a documentation page, and drawings.

The library described here has two further properties. Its templates are derived: most are generated, by the template transformation files of the library, from simpler templates, so that a family of templates shares the structure of a common ancestor. And the library records its own provenance: each derivation leaves a record, written with the library's own template-management templates.

Identification of templates

Each template of the library is identified in three ways.

IdentifierFormExample
Fully qualified nameorg.openprovenance.templates.family.Nameorg.openprovenance.templates.fs.FileTransforming
IRIhttps://openprovenance.org/templates/org/openprovenance/templates/family/Name…/fs/FileTransforming
Paththe path of the generated file, relative to the library root, without extensionorg/openprovenance/templates/fs/file-transforming

The fully qualified name identifies a template in template indexes and template transformation files; the IRI is the address of its documentation page; the path identifies the template in the library's provenance records, where the output of one derivation is the input of the next.

Each documented template has a page whose header gives its name, fully qualified name, IRI, purpose, context, design considerations and automation (the template transformation file that derives it), followed by its drawing and the details of its statements. The metadata of a page follows the model of template-pages/template.json: name, author, version, revision of, purpose, context, solution, design considerations, derived by, influenced by, bindings schemas.

Organisation

The library is the Maven module provenance-templates-library of [[TEMPLATE-LIBRARY-SOURCE]] (org.openprovenance.templates:provenance-templates-library). Its sources are in src/main/resources/:

DirectoryContent
templates/The hand-written templates, with their template index index.json.
bindings/The bindings with which template transformation files derive templates from others; their values are mostly variables.
cbindings/The bindings schemas of the templates for which code is generated.
ttfs/The template transformation files, one per derived template or family, and common-ns.json, the namespaces their bindings refer to as ${prov_ns}, ${fs_ns}, ….
catalogue/The catalogues of the template compiler, one per compiled family (fs, transport, ptm).
variable-check/The naming conventions of variables, per family ().
icons/An icon per template, named after its fully qualified name.
json-schema/The JSON Schema of template indexes.

The build executes the template transformation files (Maven goal execute-ttf) into target/generated-templates/: each derived template in PROV-N, PROV-JSONLD, PNG and SVG, and for the final templates drawings of their qualified relations, all listed in a generated template index. The JSON-LD of each final template is checked against the strict PROV-JSONLD schema (schemaCheck default-qn). The build then compiles the catalogues (goal compile-catalogue) into code in Java, Python, JavaScript and Rust.

The documentation pages, written in Markdown under template-pages/, are rendered to HTML with pandoc; template-pages/ is the root of the published site [[TEMPLATE-LIBRARY-SITE]], whose landing page lists the families with a button per template.

How templates are derived

A template of the library is derived from others in two ways [[PROV-TEMPLATE]], [[PROV-TEMPLATE-ALGORITHMS]].

  • Instantiation with variables. Instantiating a template with bindings whose values are themselves variables renames its variables and fixes some of its values: binding var:input to var:file and var:otype to fs:DataFile turns the generic Transforming1 into the file-specific FileTransforming. Binding a variable to null removes the statements or attributes that use it.
  • Merge. Merging templates that share variables composes them: Transforming1 is the merge of instantiations of the triangles Triangle1-Entity-UGD (usage, generation, derivation) and Triangle3-AGA (association, generation, attribution).

Every task of the template transformation files records its own provenance with the templates of the ptm family (). Joined, these records form the provenance of the library itself: which template was derived from which, with which bindings, and when. The build draws it in target/prov-graph/.

Families of templates

The tables list the templates that have a documentation page, with the purpose given by the page, and the other templates of each family. Each name links to the template's IRI.

primitive

Hand-written templates of a single PROV statement or a single attribute, from which the others are built: Entity0, Activity0, Agent0, Usage0, Generation0, Invalidation0, Derivation0, Association0, Attribution0, Attribution, Delegation0, Qualified-Membership0, Qualified-Specialization0, Simple-Derivation, Entity-With-Attribute.

triangles

A triangle is three PROV relations that close a cycle in a provenance graph, such as a usage, a generation and a derivation. Each triangle is a template, derived by merging primitives.

TemplatePurpose
Triangle1-Entity-UGDAn entity evolves into another entity through derivation.
Triangle1-Agent-UGDAn agent evolves into another agent through derivation.
Triangle2-Entity-SDSAn entity evolves through derivation, while retaining its identity through the specialization of a more general entity.
Triangle2-Agent-SDSAn agent evolves through derivation while remaining a specialization of a more general agent.
Triangle3-AGAAn entity is attributed to an agent associated with the activity that generated it.
Triangle4-AIAThe end of an entity (its invalidation) is attributed to an agent, responsible for its end of life.
Triangle5-GGMAn activity adds an element to a collection.

Also: Triangle6-UGM (derived, undocumented); Usage-Generation-Derivation and Association-Generation-Attribution (hand-written).

The provenance of physical things: packing, transporting, weighing. This is the family of the running example of [[PTM-BOOK]], the transport of a box. Its templates are compiled under the fully qualified names org.openprovenance.templates.transport.*.

Also, without page: EntityInit, and the composite templates PackingComposite and UnpackingComposite.

fs

The provenance of files: transformations of files by engineers following methods, and the steps of a machine-learning pipeline. Namespace fs, http://openprovenance.org/ns/fs#. The templates derive from the generic family; for example, FileTransforming instantiates Transforming1:

Also, without page: FileInit, FileTraining (a dataset fitted into a pipeline), FileValidating (a pipeline assessed into an accuracy score), FileApproving (a pipeline and its score approved), and the composite FileTransformingComposite.

Conventions

The templates of a family follow conventions, which the template transformation files check (variableCheck).

  • Variables are named after their role: an entity input, output, file, plan; an agent engineer, manager; an activity a gerund, such as transforming. A numeral distinguishes variables of the same role: input1, input2.
  • The identifiers of relations are the variables usd, gen, der, asc, attr, so that derived templates and the openprov: attributes can refer to them.
  • Each node has an open pair of attribute variables, a name and a value, such as var:oprops = 'var:ovalues' on an output and var:aprops = 'var:avalues' on an activity, through which derived templates add attributes.
  • Times are written with tmpl:startTime, tmpl:endTime and tmpl:time.

Adding a template

  1. Look for a template of the library that describes the pattern, or one from which it derives.
  2. Write bindings that derive the new template from it, in bindings/, and a template transformation file in ttfs/; or, for a new primitive, write the template in templates/ and add it to its index.
  3. Add an execution of the template transformation file to the library's build.
  4. For code generation, write its bindings schema in cbindings/ and add it to a catalogue.
  5. Write its documentation page and its icon, and add a button to the landing page.

Known issues

The following inconsistencies were found while writing this document; they are tracked in the library's TEMPLATES-TODO.md or in this document's TODO.md.

  • Eight templates have a button but no page: FileInit, FileTraining, FileValidating, FileApproving, FileTransformingComposite, EntityInit, PackingComposite, UnpackingComposite; Product2-2 has a page but no icon (T-1).
  • The pages of the physical family give fully qualified names physical.*; the build uses transport.*.
  • The page of Triangle2-Entity-SDS gives the IRI of Triangle2-Agent-SDS and the name Triangle-Entity-SDS; the template transformation file of Triangle1-Entity-UGD names it Triangle1-UGD.
  • The bindings schema cbindings/…/fs/file-merging.json is a copy of that of FileSplitting; ptm-creating.json has drifted from its template (T-9).
  • The simple family names its value variables prop_values rather than values (T-8).
  • The library's README.md gives Maven coordinates (org.openprovenance.bookptm:template-intro1) that the build no longer uses (T-3).
