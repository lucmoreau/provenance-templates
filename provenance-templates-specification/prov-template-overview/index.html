Provenance is information about the entities, activities and people involved in producing a piece of data or a thing, which can be used to form assessments about its quality, reliability or trustworthiness. PROV [[PROV-DM]] is the W3C family of specifications for expressing provenance. Applications that want to produce PROV keep writing the same patterns of provenance, again and again, with different values. Provenance templates capture these patterns declaratively: a template is a PROV document in which some identifiers, attributes and values are variables; a set of bindings associates values with the variables; instantiation replaces the variables with their values and produces an ordinary PROV document.

This document is an overview of the PROV-TEMPLATE family of documents. It introduces the approach, its concepts and its artefacts, and it guides the reader to the document that suits their needs: a primer, a specification of the formats, a specification of the algorithms, and a library of reusable templates.

This is an unofficial draft. It has no official standing of any kind and does not represent the consensus of any standards organisation.

The PROV-TEMPLATE family supersedes PROV-TEMPLATE: A Template System for PROV Documents [[PROV-TEMPLATE-2014]], an unofficial draft of 7 June 2014 edited by Danius Michaelides, Trung Dong Huynh and Luc Moreau. The 2014 draft defined templates, their expansion and a representation of bindings as PROV documents in one document. Its content is now split between [[PROV-TEMPLATE]] and [[PROV-TEMPLATE-ALGORITHMS]], and extended with the material that a decade of use has required: a JSON representation of bindings, bindings schemas, template transformation files, and a library of templates. lists the main changes.

Introduction

Generating provenance that conforms to the PROV data model [[PROV-DM]] remains a challenge for application developers. Each serialization of PROV — PROV-N [[PROV-N]], PROV-O [[PROV-O]], PROV-XML [[PROV-XML]], PROV-JSON [[PROV-JSON]], PROV-JSONLD [[PROV-JSONLD]] — has its own syntax to master, and a toolkit such as ProvToolbox [[PROVTOOLBOX]] requires programming effort that has little to do with the application itself. Worse, provenance written directly by application code is scattered across that code: what the provenance of a step looks like can only be understood by reading the program.

Yet provenance tends to follow patterns. Each time a file is uploaded, the same activity, the same generation, the same attribution to an agent is recorded, with a different file, a different time and a different agent. Provenance templates exploit this regularity. They follow three principles, already stated in [[PROV-TEMPLATE-2014]]:

  1. Declarative. A pattern of provenance is declared once, as a template whose variables act as placeholders for values; the pattern is instantiated many times, each time with a new set of bindings.
  2. Decoupled. The code that instruments an application only collects values; generating provenance from these values is left to template instantiation. The design of provenance becomes a separate concern, which can be reviewed, versioned and changed without touching the application.
  3. PROV all the way. Templates are themselves PROV documents. Every tool that reads, checks, converts or visualizes PROV applies to templates too, and no new language is introduced to write them.

A fourth principle has emerged from use, and it shapes most of what is new in this family of documents:

  1. Described and automated. Each template comes with a bindings schema that describes its variables, their types and their meaning. Bindings schemas make it possible to check bindings, to generate code that produces bindings in the application's own language, and to document templates as a library. Template transformation files automate the instantiation, merge and checking of templates as part of a build.

The approach at a glance

The figure below summarises the artefacts and the processes of the approach. Each is described in a subsection, with a pointer to the document that defines it.

Templates

A template is a PROV document whose statements contain variables. A variable is a qualified name in a reserved namespace: var: for an ordinary variable, vargen: for a variable whose value the instantiation may generate when the bindings leave it unbound. A variable can occur wherever PROV admits a qualified name: as the identifier of an entity, an activity or an agent, in the position of a relation, as an attribute, or as an attribute's value. Where PROV constrains the syntax of a value — a label is a string, a time an xsd:dateTime — a template uses an attribute of the tmpl: namespace paired with a variable. Further tmpl: attributes make a statement conditional, give a relation an identifier, or link variables so that they change value in step. Templates and the tmpl: vocabulary are defined in [[PROV-TEMPLATE]].

Bindings

A set of bindings associates variables with values. A variable may be bound to one value, to a sequence of values — the template then describes as many instances of a statement as there are values — or, for an attribute value, to a sequence of sequences, so that each instance of a statement may carry the attribute zero, one or several times. Bindings are written in JSON: a var object maps each variable to its values, written as JSON-LD value objects, and a context object declares the prefixes the values use. [[PROV-TEMPLATE]] defines this representation, and the representation of bindings as a PROV document inherited from [[PROV-TEMPLATE-2014]].

Instantiation and merge

Instantiation, also called expansion, takes a template and a set of bindings, and produces a PROV document in which no variable is left. Variables are partitioned into groups of variables that change value in step; each statement is instantiated once for each combination of the values of the groups it uses. Merge combines templates, or instantiated documents, into one. Both algorithms are specified in [[PROV-TEMPLATE-ALGORITHMS]].

Bindings schemas and generated code

A bindings schema describes the variables of a template: for each variable, the type of its values, its documentation and examples. It is the contract between an application and a template: the application promises to supply values of the declared types, and the template promises to turn them into provenance. From a template and its bindings schema, a template compiler can generate code, in the application's language, that builds bindings, writes them as compact records, and later turns logs of such records into provenance. Bindings schemas are specified in [[PROV-TEMPLATE]]; the template compiler is described there, non-normatively.

Template transformation files

A template transformation file lists tasks to be performed on templates — instantiate a template with bindings, merge templates — each writing its output in the formats requested and checking it against the PROV-JSONLD schema, so that a collection of templates can be built, rebuilt and checked automatically, for instance by a Maven build. The executions themselves leave provenance, recorded with templates. Template transformation files are specified in [[PROV-TEMPLATE]].

A library of templates

Templates are worth sharing. The same pattern of provenance — a file transformed, an item packed, an approval given — recurs across applications. A template library is a published collection of templates, each with a stable IRI, its bindings schema, its documentation and its variants. [[PROV-TEMPLATE-LIBRARY]] describes the library maintained at openprovenance.org.

Changes since PROV-TEMPLATE 2014-06-07

  • The single document of 2014 is split into a family of five documents: this overview, a primer, a specification of the artefacts, a specification of the algorithms, and a library.
  • The template vocabulary moved to http://openprovenance.org/ns/tmpl#, and gained tmpl:if, tmpl:notif and tmpl:ID; tmpl:order is written only on request.
  • Bindings are written in JSON; their representation as PROV documents is deprecated.
  • New artefacts: bindings schemas, template indexes, template transformation files, the template compiler and the template library.
  • New algorithm: merge. The treatment of unbound variables is specified per kind of statement.
  • The detailed lists are in the appendices of [[PROV-TEMPLATE]] and [[PROV-TEMPLATE-ALGORITHMS]].
